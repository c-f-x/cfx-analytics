# Behaviours

The specification is the list of what cfx-analytics must do and must not do. Each line becomes one or more tests, written before the code, and each test fails first. The harvest of 2026-10-20 completed this file (build plan step 2), and decision D-20 holds the choices it rests on.

## Format

One line per behaviour:

`ID · given … when … then … · source · decision`

- **ID** is the slice and a number, such as `intake-04`. Tests name the ID they prove.
- **Source** is where the behaviour came from: a donor test at its pinned commit (`insightflare:src/.../x.test.ts`), a flaw in a donor (`traks`), PostHog's SDK or docs, a consumer's own code, or `ours`.
- **Decision** is `keep`, `adapt` (then say how), or `reject`. A rejected behaviour stays in the list, so nobody adds it back by accident.

## How to harvest

1. Clone each donor at its pinned commit (`docs/donors.md`) into a temp folder, and remove the folder with `trash` afterwards.
2. Read its tests for the slices we have. Note each behaviour that holds through a public boundary (an HTTP request, an RPC call, a pure function's input and output). Skip tests of a donor's private internals and tests written only to raise coverage.
3. Never copy a test file. Write the behaviour line. Our test is then written against our own interfaces.

| flarelytics (717) | worker query templates, input validation |
