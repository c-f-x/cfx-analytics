# Spike S1: one ProjectStore answers the dashboard

Run on 2026-10-20 under `wrangler dev` 4.151.2, on the owner's Mac (Apple M5 Pro, 18 cores, load average 3.4 to 3.8, Node 26.8.1). The code lived on the branch `spike/s1` and is not on master. The numbers are local. Production runs on other hardware, so treat them as a guide to scale, not a promise.

## Verdict

Every query passed on the second run, and so did the batch alone. One pass line failed, and the cause is structural. A batch that arrives while a query runs waits for the query, because the object runs one call at a time. My recommendation is to accept S1 with that line restated, as set out under "What needs the owner's go".

## The fixture

The fixture holds 2,000,000 events with 50 names, 20,000 people over 13 months, and 50,000 heatmap points. Each row is a pure function of a seed and its index, so the object generated its own rows. With the five event indexes the database is 1.06 GB, about 530 bytes an event.

## The timer's known case

The run first asked the object to sleep 200 ms three times and 1,000 ms once. Measured from outside, the sleeps took 209 to 230 ms and 1,013 ms, so the outside timer is trusted. Locally, the object's own clock also moves without I/O: a busy loop read 167 ms inside and 173 ms outside. Deployed Workers hold the clock still while code runs without I/O, so a timing taken inside a deployed object would read 0. Every number below is taken outside the object.

## Results

Times are the median and maximum of five warm runs, in ms. The pass lines are 2,000 ms for a query and 100 ms for a batch.

Loading 2,000,000 events in 20,000-row transactions took 189 s with four event indexes and 215 s with five.

## What changed between the runs

On run 1, retention grouped every event by person to find each person's first event. Each of the 2,000,000 index entries then had to be read from the table to check `bot` and `internal`, so the query read 7.75 million rows. Run 2 added a partial index, `events_person_counted` on `(person_id, ts) WHERE bot = 0 AND internal = 0`. It looks each person up once, and each week's activity with one `EXISTS`. Every lookup is answered from the index alone. The cost is about 14% more load time, while a batch stays near 13 ms.

## Findings for the real build

1. **Intake waits behind queries.** The batch's wait equals the running query's time. The SDKs time a request out after 60 s (posthog-js) or 10 s (posthog-node, posthog-ios), and they retry. So a wait of a few hundred milliseconds loses nothing. The risk is a query that runs for many seconds. A rows-read budget per query bounds it, and `docs/engineering.md` already prefers that kind of budget to a time.
2. **The daily cap and the object's size limit disagree.** At 530 bytes an event, one object's 10 GB holds about 19 million events. The default cap of 200,000 events a day, kept for 395 days, allows 79 million. The cap and the retention need to fit the size, or the object needs a size guard.
3. **Local workerd refuses `jurisdiction("eu")`.** It throws "Jurisdiction restrictions are not implemented in workerd", and wrangler has no jurisdiction setting for a Durable Object binding. As designed, `apps/worker/src/platform/project-store-id.ts` cannot run in the Workers test pool.
4. **`rowsWritten` counts index entries.** Three events with five indexes report 18. The number of rows inserted has to come from `INSERT ... RETURNING`.
5. **A bound JavaScript number reaches SQLite as a REAL.** Integer division needs `CAST(? AS INTEGER)`.
6. **A run left wrangler's processes behind,** and its own check reported nothing. That is fixed in pull request #3: a run records a process group and stops all of it.

## What the owner decided

The owner restated the batch line (D-18) and left the jurisdiction call to Claude (D-19). The recommendations below are kept as they were made.

## What needed the owner's go

- **Restate the batch line.** It would read: "a batch waits no longer than the longest dashboard query, and each query reads no more than its rows budget". I recommend it, for the reasons in finding 1. The alternative is a second object that takes intake while the ProjectStore answers queries. That is a second writer with its own data lifetime, and nothing measured here calls for it.
- **The jurisdiction gap (finding 3).** I recommend this: the composition root passes the ProjectStore namespace in. Production passes `env.PROJECT_STORE.jurisdiction("eu")`, and the tests pass the plain namespace. A test then reads the deployed config and fails if any path builds the namespace without the jurisdiction. This is environment-dependent wiring, which needs the owner's approval under the no-fallbacks rule.
